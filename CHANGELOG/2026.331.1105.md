# 2026.331.1105 — feat(vnc): the screenshot artifact can be OCR-asserted (artifact_contains_text)

## Summary

Closes opencharly/plugin-vnc#7.

A plan could assert that a `vnc: screenshot` artifact EXISTS and is not uniform, but not what it
SHOWS: an authored `vnc: {method: screenshot, artifact_contains_text: …}` was rejected by the host with
`#VncInput.artifact_contains_text: field not allowed`, because the field lived in the shared SDK
validator but not in this plugin's own CUE schema.

- **`candy/plugin-vnc/schema/vnc.cue`** — `artifact_contains_text?: string @go(ArtifactContainsText)`
  beside the other artifact validators, with the host-side-OCR prerequisite stated where an author
  reads it (`tesseract` + language data on the HOST; the validator says so rather than reporting a
  missing engine as "text not found").
- **`candy/plugin-vnc/params/cue_types_gen.go`** — the field, in the file's own yaml+json tag style. The
  pinned `cue` here (v0.16.1) emits json-only tags, so it cannot reproduce this file byte-for-byte; the
  schema is the source of truth and a regeneration re-emits the same field.
- **A stray `cue_types_gen.go` at the repo root** from my first generation attempt is removed in the
  second commit (it was never part of the change).
- The generated file's yaml+json tag convention is PRE-EXISTING (every field in it carries both); the
  new field follows it, so this adds no drift of its own.

Nothing else in the verb changed: the provider already hands the raw op to `sdk.VerbVerdict`, whose
`RunArtifactValidators` implements the OCR check.

### Spike

**RCA claim.** The host validates every authored `vnc:` step's `plugin_input` against the plugin's
OWN declared `#VncInput` (served over the Describe channel). `sdk.RunArtifactValidators` already
implements `artifact_contains_text`, and the provider already hands the raw op to
`sdk.VerbVerdict` — so the defect is exactly one missing DECLARATION, and nothing else.

Candidates, each measured:

```
# (a) declare the field in the plugin's CUE schema, let the SDK validator run (CHOSEN)
PASS  probe: open a blank tab                                               Opened about:blank (tab 2941…)
PASS  probe: paint a known word into the page                              PAINTED
PASS  probe: vnc screenshot ACCEPTS artifact_contains_text and OCR finds the word
                                                                           Screenshot saved to /tmp/vnc-probe.png
92 steps: 86 passed, 0 failed, 6 skipped                                   (exit rc=0)
# and it FAILS when the word is absent — same step, earlier run:
vnc: screenshot: artifact_contains_text: "CHARLYPROBE" not found in the text OCR read from
"/tmp/vnc-probe.png" (read 260 characters; first 200: "b ® vnc-probe * -+ — 1= x € > G …")

# (b) implement the OCR check inside the plugin instead of declaring the field
$ (the rejection this issue starts from, before any change)
#VncInput.artifact_contains_text: field not allowed
# → not a viable candidate: the rejection happens in HOST-side validation of authored input against
#   the plugin's declared schema, so code inside the plugin cannot accept a field its schema does not
#   declare. It would also duplicate sdk.RunArtifactValidators (R2).

# (c) leave OCR to each consumer, host-side (the status quo this repo's bed uses today)
PASS  the STREAMED FRAME shows the page's own text — OCR of the recorded desktop stream
      [bed-vnc-shows-page] (attempts=2, elapsed=10.271s)                    (exit=0)
# → works, but pushes a tesseract invocation into every consumer's bed and cannot be expressed in a
#   plan at all: exactly the gap this issue names.
```

Winner: **(a)** — one declaration, the SDK's single implementation runs, and the assertion both
passes on a painted word and fails on an absent one. The RCA verdict holds: the missing link was the
schema declaration, and the measurement could not have gone green otherwise.
